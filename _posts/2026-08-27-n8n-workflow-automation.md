이미지 매칭 파이프라인을 만들다 보니, 같은 작업을 손으로 반복하는 지점이 계속 눈에 띄었다. 새 데이터 파일이 도착하면 스크립트를 돌리고, 결과를 확인하고, 필요하면 알림을 보내는 흐름인데, 지금은 이걸 전부 터미널에서 순서대로 실행하고 있다. 이런 "트리거 → 실행 → 후속 조치"를 자동으로 이어주는 도구가 n8n이다.

## n8n이 뭔가

n8n은 오픈소스 워크플로우 자동화 도구다. Zapier나 Make와 같은 카테고리에 속하지만, 노드 기반 화면에서 워크플로우를 조립하고 직접 서버에 올려 운영할 수 있다는 점이 다르다.

구성 방식은 단순하다.

- **트리거 노드**: 워크플로우의 시작점. 웹훅 수신, 정해진 시간(cron), 폴더 변경 감지 같은 조건으로 실행된다.
- **액션 노드**: 실제 작업. HTTP 요청, 데이터베이스 조회, 메시지 발송, 파일 처리 등이다.
- **로직 노드**: 조건 분기나 데이터 변환을 담당한다.

노드 사이에는 JSON 데이터가 흐르고, 대부분의 노드는 입력받은 데이터 각각에 대해 자동으로 반복 실행된다. 별도의 반복문을 짤 필요가 없다는 뜻이다.

## 코드와의 경계

n8n이 무거운 연산 자체를 대신해주는 건 아니다. 이미지 해싱이나 임베딩 계산은 여전히 Python이 해야 한다. n8n의 역할은 그 앞뒤를 잇는 것이다.

- **Code 노드**로 짧은 JavaScript나 Python을 워크플로우 안에 바로 넣을 수 있고
- **HTTP Request 노드**로 별도로 띄워둔 API를 호출할 수 있고
- 서버에 직접 올린 경우 **Execute Command 노드**로 셸 명령을 그대로 실행할 수도 있다

즉 "무엇을 언제 실행하고, 결과를 어디로 보낼지"를 담당하는 오케스트레이션 계층이라고 보면 된다.

## 매칭 파이프라인에 적용해본다면

최근 마무리한 작업 하나를 예로 들어본다. 자사몰과 협력몰에 등록된 상품 이미지를 대조해서 같은 상품을 찾아내는 파이프라인인데, 각 이미지의 지각 해시(perceptual hash)를 계산한 뒤 서로 다른 두 목록 사이의 해시 거리를 비교해 가까운 순으로 후보를 추리고, 애매한 건 사람이 직접 이미지를 보고 확정하는 방식으로 만들었다.

이 파이프라인은 이미 완성된 상태고, 여기에 n8n을 적용한다고 가정하면 이런 그림이 나온다.

**신규 데이터 감지 → 매칭 실행 → 요약 전달**: 새 상품 목록 파일이 도착하면 자동으로 매칭 스크립트를 실행하고, 신규로 확정된 매칭 건수와 대기 중인 건수를 요약해서 담당자에게 전달한다. 지금은 이 과정을 매번 직접 실행하고 결과를 확인하고 있는데, 파일 도착을 감지하는 트리거 하나만 추가하면 나머지는 그대로 자동화 대상이다.

**리뷰 결과 후속 처리**: 사람이 직접 확인해야 하는 판단(이미지 두 장이 같은 상품인지 보는 것)은 자동화 대상이 아니다. 하지만 리뷰 결과 파일이 갱신될 때마다 최종 결과를 다시 취합하고 공유 문서에 반영하는 건 자동화할 수 있다.

**인프라 상태 확인**: 데이터베이스나 검색 엔진 컨테이너가 정상 동작하는지 주기적으로 확인하고, 문제가 생기면 알림을 보내는 흐름도 흔한 사용 사례다.

## 서비스가 늘어날 때 생기는 문제

n8n을 기존 인프라에 추가하면 자연스럽게 포트가 하나 더 늘어난다. 지금도 검색 엔진, 데이터베이스, 웹 대시보드가 각각 다른 포트를 쓰고 있는 상태라, 서비스가 늘수록 어느 포트가 뭘 위한 건지 관리하기가 번거로워진다.

이럴 때 표준적인 해법은 **리버스 프록시**를 앞단에 두는 것이다. 외부에 노출하는 포트를 하나로 줄이고, 그 뒤에서 프록시가 요청 경로를 보고 알맞은 내부 서비스로 전달해준다.

```
외부 요청 ──▶ 포트 하나(프록시)
                 │
     ┌───────────┼───────────┐
     ▼           ▼           ▼
  대시보드      n8n        검색엔진
 (내부 전용)  (내부 전용)   (내부 전용)
```

나머지 서비스들은 호스트에 포트를 직접 열지 않고 같은 내부 네트워크 안에서만 서로 통신한다. 데이터베이스처럼 웹 프로토콜을 쓰지 않는 서비스는 애초에 프록시 대상이 아니라, 아예 외부 노출 없이 내부 전용으로 돌리면 된다.

프록시 도구로는 Traefik이 잘 맞는 편이다. 서비스를 추가할 때마다 설정 파일을 새로 고칠 필요 없이, 각 서비스에 짧은 설정 몇 줄만 붙이면 자동으로 인식하기 때문이다. 서비스 구성이 계속 바뀌는 초기 단계 프로젝트에는 이 쪽이 관리 부담이 적다.

## 정리

n8n은 계산을 대신해주는 도구가 아니라, 이미 짜둔 스크립트들을 언제 실행하고 결과를 어디로 보낼지 이어주는 접착제에 가깝다. 반복되는 실행-확인-알림 과정이 있다면 자동화 후보고, 사람이 직접 판단해야 하는 부분은 그대로 남겨두면 된다. 서비스가 하나씩 늘어나는 시점이라면, n8n 도입과 별개로 리버스 프록시로 진입점을 정리해두는 것도 함께 고려할 만하다.
