상담 중 고객이 방금 한 말을 받아서, 그에 맞는 대응 매뉴얼을 찾아 상담원 화면에 띄우는 흐름을 만들었다. 


## 세운 것

`docker compose`로 n8n, Qdrant, PostgreSQL을 올리고 Ollama는 맥에 직접 설치.

```
맥 호스트
  Ollama :11434   ← 컨테이너 밖
     bge-m3      임베딩
     llama3.2    문장 생성
  ┌ Docker ─────────────────┐
  │ n8n :5678               │
  │ Qdrant :6333            │
  │ PostgreSQL              │
  └─────────────────────────┘
```

Ollama를 컨테이너에 안 넣은 이유는 도커 컨테이너가 애플 GPU(Metal)를 직접 못 쓴다. 
안에 넣으면 CPU로만 돌아 느려진다. 그래서 컨테이너 안의 n8n이 `host.docker.internal:11434`로 호스트를 찾아가게 했음.
컨테이너에서 실제로 닿는지부터 확인하고 넘어갔다.

```
docker exec cs_n8n nc -z -w2 host.docker.internal 11434   # OK
```

Qdrant는 볼륨을 붙여 영속화. 

## 매뉴얼 적재 — 임베딩에 뭘 넣을지가 갈렸다

매뉴얼 15조각을 bge-m3로 임베딩해 Qdrant에 넣었다. 
여기서 예상이 틀린 게 하나 있다. 처음엔 제목과 본문을 합쳐 임베딩하는 게 당연히 낫다고 생각했다. 제목에 핵심어가 들어있으니까. 구성을 바꿔가며 네 가지를 비교해봤다.

| 임베딩에 넣은 것 | top-1 | top-3 |
|---|---|---|
| **본문만** | 14/18 (77.8%) | **18/18 (100%)** |
| 제목 + 본문 | 14/18 (77.8%) | 16/18 (88.9%) |
| 분류 + 제목 + 본문 | 14/18 (77.8%) | 16/18 (88.9%) |
| 분류 + 제목 반복 강조 | 14/18 (77.8%) | 16/18 (88.9%) |

top-1은 무엇을 해도 14/18에서 꿈쩍하지 않고, top-3만 움직였다. 그리고 제목을 붙일수록 **떨어졌다.**

제목은 "로켓배송 지연 응대" 같은 짧은 명사구다. 이게 벡터를 문서 제목 쪽으로 끌어당겨서, "어 그 제가 주문한 게 분명히 어제 온다고 했는데" 같은 구어체 발화와의 정렬을 오히려 방해한 것으로 보인다. 검색어와 검색 대상의 **문체가 얼마나 닮았는지**가, 핵심어가 들어있는지보다 크게 작용했다.



## 검색만 놓고 보면

발화 18건을 넣어 채점했다.

| 지표 | 결과 |
|---|---|
| top-1 적중 | 14/18 (77.8%) |
| top-3 적중 | **18/18 (100%)** |
| 임베딩 | 49ms |
| 검색 | 6ms |

정답이 항상 상위 3개 안에 있었다. 

## 에이전트를 붙였더니 나빠졌다

원래 계획은 n8n의 AI Agent 노드를 놓고 매뉴얼 검색을 도구로 물리는 것이었다. 에이전트가 발화를 읽고 판단해서 도구를 고르는 그림이다. 그렇게 만들었더니 결과가 반대로 나왔다.

| 구성 | 실질 정확도 | 평균 지연 |
|---|---|---|
| 검색만 (top-3) | 100% | 55ms |
| 에이전트 + 도구 (llama3.2, 긴 도구설명) | 61.1% | 9.7초 |
| 에이전트 + 도구 (설명 축약) | 측정 불가 | 실행이 멈춤 |
| 에이전트 + 도구 (규칙 우선, 반복 상한) | 55.6% | 23.7초 |
| 에이전트 + 도구 (qwen2.5:7b) | 신뢰 불가 | 7.2초 |

세 번 다른 방향으로 손봤는데 전부 실패했다. 왜 그런지는 n8n 실행 이력을 뜯어보고 알았다.

### 3B 모델은 발화를 그대로 넘기지 않는다

"웹훅으로 들어온 원문"과 "에이전트가 검색 도구에 넣은 문장"을 대조했다. **25건 중 21건이 달랐다.**

| 어떻게 달라졌나 | 실제로 나온 것 |
|---|---|
| 도구 설명문을 검색어로 복사 (5건) | "고객 대응 매뉴얼을 유사도로 검색한다. 배송지연, 환불…" |
| 영어로 번역 | "제가 시킨 거랑 아예 다른 물건이 왔어요" → `color difference and new product` |
| 한 단어로 줄임 | "단순 변심인데 반품하면 배송비가 얼마나…" → `반품` |
| 글자가 뒤바뀜 | `해외카드` → `외해카드` |

검색은 멀쩡한데 **입력이 오염되고 있었다.** 도구 설명문을 통째로 복사하면 모든 분류 단어가 검색어에 들어가서, 결국 가장 일반적인 매뉴얼이 걸린다. 채점표의 실패 위치와 정확히 겹쳤다.

설명문이 길어서 복사된다고 보고 짧게 줄였다. 그랬더니 이번엔 에이전트가 도구를 반복해서 부르며 실행이 멈췄다. 그리고 그 대기 요청들이 Ollama 큐를 막아, 관계없는 직접 호출까지 90초 넘게 걸리는 상태가 됐다. 재시작으로만 풀렸다.


## 검색을 에이전트 손에서 제거

발화 원문으로 검색을 먼저 돌리고,  **모델이 검색어를 쓰지 않게 구조를 바꿈.**

```
[웹훅] 발화
  → [Qdrant 검색] 발화 원문 그대로, 상위 3개    ← 모델이 손댈 수 없는 구간
  → [후보 합치기]
  → [LLM] 후보 중 선택 + 안내 작성
  → [응답]
```

| | 에이전트 구조 | 바꾼 구조 |
|---|---|---|
| 실질 정확도 | 55.6% | **77.8%** |
| 인용 번호 정답 | 27.8% | **77.8%** |
| 인용 형식 준수 | 61.1% | **100%** |
| 평균 지연 | 23.7초 | **4.7초** |
| 최대 지연 | 120초(시간 초과) | **6.6초** |

## 겪은 것

**Qdrant 포인트 번호에 'M001'을 못 넣는다.** 정수나 UUID만 받는다. 순번을 번호로 쓰고 매뉴얼 번호는 payload에 담았다. 그리고 payload 구조를 `content`와 `metadata`로 나눠뒀더니, 같은 컬렉션을 파이썬 스크립트와 n8n이 그대로 공유할 수 있었다.
