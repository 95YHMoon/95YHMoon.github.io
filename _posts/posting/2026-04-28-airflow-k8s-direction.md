이번 구간은 개념 논의가 길었던 만큼, 실제로 확정된 것만 추려서 기록한다.

## 1. 프로젝트의 이중 목적 확정

이 MLOps 파이프라인 작업은 시계열 수요예측이라는 실제 필요 외에, **취업 준비용 교두보**로도 활용한다는 전제가 깔려있음을 확인했다.

- 타겟 직무는 MLOps/ML 엔지니어, 데이터 사이언티스트/분석가, 데이터 엔지니어 세 갈래를 모두 열어두고 역량을 쌓는 중 (데이터사이언스 석사 과정 병행 중).
- 세 갈래 중 **데이터사이언스는 별도 트랙으로 다루고, 데이터 엔지니어링(DE)과 MLOps는 하나의 축으로 묶어서 학습**하기로 결정 — 두 분야가 실무에서도 수렴하는 추세라는 판단.

## 2. 학습 진행 방식 확정 (프로토콜)

여러 번 진행 방식에 대한 피드백을 거쳐, 앞으로는 새로운 기술 주제마다 아래 순서를 지키기로 확정했다:

1. **개념** — 왜 필요한지, 기존에 아는 것과 어떻게 연결되는지
2. **예시/최소 형태** — 업계 사례 포함한 구체적인 모양
3. **성공 기준 합의** — "이게 되면 끝난 것"을 미리 정함
4. **구현** — 명령어/코드를 설명과 함께 텍스트로 제시하고, 실제 실행·트러블슈팅은 직접 진행. 학습 목적상 중요한 명령은 대신 실행해주지 않음
5. 큰 덩어리로 몰아가지 않고 단계마다 확인

## 3. 아키텍처 논의에서 확정된 결론

- **Databricks는 "기능이 한정적"이라기보다, Spark/Delta Lake라는 하나의 패러다임에 수직 통합된 플랫폼이라 그 틀 밖의 임의 워크로드에 대한 유연성이 낮은 것**이 정확한 평가.
- 장기적으로 규모가 커질 경우 **K8s는 이기종 워크로드를 하나의 컴퓨트 풀에 효율적으로 bin-packing한다는 점에서 사실상 필수불가결**하다는 데 합의.
- Airflow에서 이 사고가 그대로 적용되는 지점이 **KubernetesExecutor** — 태스크마다 K8s Pod를 그때그때 만들었다 없애는 방식으로, LocalExecutor(격리 없음)/CeleryExecutor(고정 워커 풀, 유휴 자원 낭비)보다 자원 효율이 높다.
- 지금 만들어둔 **DockerOperator 기반 구성은 KubernetesExecutor의 축소판**(단일 도커 호스트에서만 동작, 멀티노드 스케줄링/자원 limit 강제 불가)이라는 위치로 정리됨.
- **KubernetesExecutor는 K8s 클러스터가 이미 떠있어야 하는 전제 조건**이며, Airflow가 클러스터 자체를 만들어주지는 않는다.

## 4. 지금 상태

Airflow를 docker-compose 컨테이너로 추가하고(LocalExecutor 기준, Celery/Redis는 규모상 제외), `DockerOperator`로 기존 `pipeline` 이미지를 형제 컨테이너로 실행하는 DAG까지는 붙였다. UI 기동과 DAG 파일 import까지는 확인했는데, **끝까지 트리거해서 도는지는 아직 검증 전**이다 — DockerOperator가 결국 KubernetesExecutor의 축소판(단일 호스트 한정)이라는 걸 위에서 정리한 참이라, 이 검증보다 K8s 전환이 먼저라고 판단했다.

## 5. 다음 단계 (착수 전 — 방향만 확정)

- 이 단계부터는 실행/트러블슈팅을 직접 진행하기로 함 (위 프로토콜 4번 적용)
