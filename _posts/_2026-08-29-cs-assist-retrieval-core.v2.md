상담 중 고객이 방금 한 말을 받아서, 그에 맞는 대응 매뉴얼을 찾아 상담원 화면에 띄우는 흐름을 만들었다.

## 세운 것

`docker compose`로 n8n, Qdrant, PostgreSQL을 올리고 Ollama는 맥에 직접 설치.

```
맥 호스트
  Ollama :11434   ← 컨테이너 밖
     bge-m3      임베딩
     llama3.2    문장 생성
  ┌ Docker ─────────────────┐
  │ n8n :5678               │
  │ Qdrant :6333            │
  │ PostgreSQL              │
  └─────────────────────────┘
```

도커 컨테이너가 애플 GPU(Metal)를 못 쓴다. 안에 넣으면 CPU로만 돌아 느려짐. 그래서 컨테이너 안의 n8n이 `host.docker.internal:11434`로 호스트를 찾아가게 했다.

닿는지부터 확인하고 넘어갔다.

```
docker exec cs_n8n nc -z -w2 host.docker.internal 11434   # OK
```

Qdrant는 볼륨을 붙여 영속화.

## 매뉴얼 적재

매뉴얼 15조각을 bge-m3로 임베딩해 Qdrant에 넣었다.

처음엔 제목과 본문을 합쳐 넣는 게 낫다고 생각했다. 제목에 핵심어가 있으니까. 구성을 바꿔가며 네 가지를 비교했더니 반대로 나왔다.

| 임베딩에 넣은 것 | top-1 | top-3 |
|---|---|---|
| 본문만 | 14/18 | 18/18 |
| 제목 + 본문 | 14/18 | 16/18 |
| 분류 + 제목 + 본문 | 14/18 | 16/18 |
| 분류 + 제목 반복 강조 | 14/18 | 16/18 |

top-1은 뭘 해도 14/18. 제목을 붙일수록 top-3만 떨어졌다.

제목은 "로켓배송 지연 응대" 같은 짧은 명사구다. 이게 벡터를 문서 제목 쪽으로 끌어당기는 것 같은데, 정확히 왜 구어체 발화와의 정렬을 방해하는지는 아직 모르겠다. 다만 이 규모에서는 본문만 넣는 쪽이 확실히 나았다.

## 검색만 놓고 보면

발화 18건을 넣어 채점했다. top-1은 14건, top-3은 18건 전부. 임베딩 49ms에 검색 6ms.

## 에이전트 구조부터

원래 계획은 n8n의 AI Agent 노드를 놓고 매뉴얼 검색을 도구로 물리는 것이었다. 에이전트가 발화를 읽고 판단해서 도구를 고르는 그림.

| 구성 | 정확도 | 평균 지연 |
|---|---|---|
| 검색만 (top-3) | 100% | 55ms |
| 에이전트 + 도구 (llama3.2, 긴 도구설명) | 61.1% | 9.7초 |
| 에이전트 + 도구 (설명 축약) | 측정 불가 | 실행이 멈춤 |
| 에이전트 + 도구 (규칙 우선, 반복 상한) | 55.6% | 23.7초 |
| 에이전트 + 도구 (qwen2.5:7b) | 신뢰 불가 | 7.2초 |

세 번 다른 방향으로 손봤는데 전부 실패. 원인은 n8n 실행 이력을 뜯어보고 알았다.

### 3B는 발화를 그대로 안 넘긴다

웹훅으로 들어온 원문과, 에이전트가 검색 도구에 넣은 문장을 대조했다. 25건 중 21건이 달랐다.

| 어떻게 달라졌나 | 실제로 나온 것 |
|---|---|
| 도구 설명문을 검색어로 복사 (5건) | "고객 대응 매뉴얼을 유사도로 검색한다. 배송지연, 환불…" |
| 영어로 번역 | "제가 시킨 거랑 아예 다른 물건이 왔어요" → `color difference and new product` |
| 한 단어로 줄임 | "단순 변심인데 반품하면 배송비가 얼마나…" → `반품` |
| 글자가 뒤바뀜 | `해외카드` → `외해카드` |


모델을 키우면 나을까 싶어 qwen2.5:7b로 바꿨다. 20건 중 1건만 도구를 불렀다. 나머지는 검색을 건너뛰고 자기 지식으로 답하면서 매뉴얼 번호를 지어냈다. 해외카드 환불을 "7일에서 30일"이라고 했는데 매뉴얼 값은 3~7일, 해외카드 14일이다.

3B는 검색어를 망치고 7B는 검색을 건너뛴다. 방향은 반대인데 결과는 둘 다 실패.

## 검색을 에이전트 손에서 제거

발화 원문으로 검색을 먼저 돌리고, 모델이 검색어를 쓰지 않게 구조를 바꿈.

```
[웹훅] 발화
  → [Qdrant 검색] 발화 원문 그대로, 상위 3개    ← 모델이 손댈 수 없는 구간
  → [후보 합치기]
  → [LLM] 후보 중 선택 + 안내 작성
  → [응답]
```

| | 에이전트 구조 | 바꾼 구조 |
|---|---|---|
| 정확도 | 55.6% | 77.8% |
| 인용 번호 정답 | 27.8% | 77.8% |
| 인용 형식 준수 | 61.1% | 100% |
| 평균 지연 | 23.7초 | 4.7초 |
| 최대 지연 | 120초(시간 초과) | 6.6초 |

정확도보다 눈에 띈 건 두 번째 줄이다. "응답 본문이 어느 매뉴얼에서 왔나"와 "모델이 어느 매뉴얼을 썼다고 밝혔나"를 따로 쟀는데, 바꾼 구조에서는 둘 다 77.8%로 같았다. 에이전트 구조에서는 55.6% 대 27.8%로 벌어져 있었다. 답은 그럴듯한데 출처가 엉뚱했다는 뜻.

## 늘어난 워크플로우

| 주소 | 구조 | 정확도 |
|---|---|---|
| `POST /webhook/assist` | AI Agent + 검색 도구 | 55.6% |
| `POST /webhook/assist-rag` | 검색 고정 + LLM 선택 | 77.8% |

실패한 쪽도 안 지웠다.

## 겪은 것

Qdrant 포인트 번호에 'M001'을 못 넣는다. 정수나 UUID만 받음. 순번을 번호로 쓰고 매뉴얼 번호는 payload에 담았다. payload를 `content`와 `metadata`로 나눠뒀더니 같은 컬렉션을 파이썬 스크립트와 n8n이 그대로 공유할 수 있었는데, 이건 처음부터 노린 건 아니고 하다 보니 그렇게 됐다.
