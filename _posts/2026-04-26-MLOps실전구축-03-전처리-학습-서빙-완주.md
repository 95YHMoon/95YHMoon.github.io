2편에서 수집 단계까지 끝냈다. 이번 편에서 전처리 → 학습 → 서빙을 붙여서, 수집-전처리-학습-서빙 네 단계를 처음으로 끝까지 돌렸다.

## 전처리 (`preprocess.py`)

기존 노트북 로직 — 연도별 시트에서 타깃 품목만 골라 항목 문자열에서 스텝·월을 파싱하고, 스텝별로 월별 리샘플링 — 을 그대로 함수로 옮겼다. 딱 하나만 고쳤다. 원본 노트북은 리샘플 범위의 끝을 특정 날짜로 하드코딩해뒀는데, 이러면 나중에 데이터가 더 들어와도 파이프라인이 조용히 그 시점에서 멈춘다. 그래서 실제 데이터의 최신 날짜를 기준으로 동적으로 계산하게 바꿨다.

### 삽질: "1년 밀림" 오해

전처리 결과를 기존 레거시 파일과 비교했더니 특정 스텝에서 값이 정확히 1년씩 밀려 나왔다. "롤오버 처리가 안 된 버그구나" 싶어서 고치려던 참이었다. 그런데 알고 보니 그게 의도된 정규화였고, 오히려 레거시 파일 쪽이 예전 로직으로 만들어진 stale 파일이었다. 남의 코드(과거의 나 포함)를 고치기 전에 "왜 이렇게 짰지"부터 확인해야 한다는 걸 또 배웠다.

## 학습 (`train.py`)

앞서 정리했듯 실제로 쓰는 모델은 Transformer가 아니라 SARIMA다. 학습 스크립트의 흐름은 이렇다.

1. 전처리 산출물에서 지정한 `--step`의 시계열만 고른다
2. `log1p` 변환 후 마지막 N개월을 테스트셋으로 뗀다
3. `SARIMAModel()`로 auto_arima 학습
4. MAE/RMSE/MAPE를 계산해 `log_metrics()`
5. 학습된 모델을 `pyfunc.PythonModel`로 감싸 Model Registry에 바로 등록

모델을 바꾼 효과가 여기서 서빙 설계까지 이어진다. Transformer였다면 입력 두 개와 별도 스케일러들을 함께 아티팩트로 묶어야 해서, 서빙용 래퍼를 학습과 분리된 단계로 나중에 따로 만들어야 했을 것이다. 반면 SARIMA는 학습이 끝난 시점에 예측에 필요한 게 전부 모델 객체 하나에 들어있어서(`predict(horizon)`만 부르면 끝), 학습하면서 바로 pyfunc로 감싸 등록해버릴 수 있었다. 모델 하나 바꿨을 뿐인데 서빙까지 단순해졌다.

```
[train] step=2 order=ARIMA(0,0,0)(2,0,0)[12] [auto]
[train] metrics={'mae': 1617, 'rmse': 1785, 'mape': 42.17}
Successfully registered model 'sales-forecast'. version 1
```

MAPE가 42%로 높게 나왔다. 테스트 구간(2024-08~12)이 실제로는 "아직 매출 기록이 없는" 달인데 전처리에서 0으로 채워졌기 때문이다. 매출이 폭락한 게 아니라 데이터 미기록 구간이라, 지금 이 숫자는 액면 그대로 믿으면 안 된다. 일단 인지만 해두고 넘어간다. 원인 분석과 개선은 4편에서 본격적으로 다룬다.

## 서빙 (`mlflow models serve`)

레지스트리에 등록된 모델을 바로 REST로 띄웠다.

```bash
mlflow models serve -m "models:/sales-forecast/1" \
  --host 0.0.0.0 --port 5002 --env-manager local
```

여기서 `--env-manager local`이 핵심이다. 기본값은 학습 당시 환경을 conda로 새로 만들어 격리하는 것인데, `pipeline` 이미지에 이미 학습과 똑같은 의존성이 있으니 그럴 필요가 없다. 지금 파이썬 환경을 그대로 쓰게 했다.

```bash
curl -X POST http://localhost:5002/invocations \
  -H "Content-Type: application/json" \
  -d '{"dataframe_split": {"columns": ["horizon"], "data": [[6]]}}'
```

응답값이 학습 때 확인한 예측과 정확히 같았다. Registry에 저장된 모델을 REST로 불러온 게 검증된 것이다.

## 한 바퀴 요약

```
collect.py    → data/raw/sales_<timestamp>.xlsx
preprocess.py → data/processed/sales_resample.xlsx
train.py      → mlflow run + Model Registry v1
serve         → mlflow models serve → REST /invocations
```

수집-전처리-학습-서빙 네 단계가 로컬 docker-compose(postgres + mlflow-server + pipeline) 위에서 전부 이어졌다.
