## kind로 멀티노드 클러스터 만들기

기본값(`kind create cluster`)은 노드 1개다. control-plane과 worker를 겸한다. 여러 노드를 원하면 설정 파일로 명시한다.

```yaml
# kind-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
nodes:
  - role: control-plane
  - role: worker
  - role: worker
```

`nodes:` 항목 하나가 컨테이너 하나이자 노드 하나다. 여기서 알아둘 게 있다. control-plane 노드는 기본적으로 taint가 걸려서 일반 워크로드가 배치되지 않는다. 관리 기능이 일반 작업 부하와 자원을 다투지 않게 하려는 설계다. 그래서 실제 애플리케이션을 올리려면 worker가 최소 1개는 있어야 한다.

## Pod / Deployment / ReplicaSet 계층

워크로드 오브젝트는 계층을 이룬다.

```
Deployment  ("이 템플릿으로 N개 유지해라")
    ↓
ReplicaSet  ("지금 몇 개 떠있나 세고 부족하면 채움")
    ↓
Pod × N     (실제 컨테이너가 도는 단위)
```

Pod를 단독으로 만들면 하나 만들어지고 끝이다. 죽어도 다시 안 살아난다. 반면 Deployment로 만들면 세 오브젝트가 다 생기고, Pod 이름도 자동으로 붙는다. 그리고 Deployment는 Pod를 이름이 아니라 라벨로 추적한다. selector와 template의 라벨이 같아야 서로 연결된다는 점을 놓치기 쉽다.

`replicas: N`으로 만들면 스케줄러가 이들을 worker 노드에 나눠 배치한다(`kubectl get pods -o wide`의 `NODE` 컬럼으로 분산 확인). K8s가 자원을 여러 노드에 걸쳐 쓰는 가장 기본적인 그림이다.

## 자주 쓰는 조회 패턴

| 명령 | 용도 |
|---|---|
| `kubectl get pods` | 현재 상태 스냅샷 |
| `kubectl get pods -w` | `ContainerCreating → Running` 전이를 실시간으로 |
| `kubectl get pods -o wide` | `NODE`/`IP` 컬럼 추가 |
| `kubectl logs <pod>` | 컨테이너 stdout |
| `kubectl describe pod <pod>` | 배치 노드·이벤트 로그 등 상세 |

## docker-compose ↔ kind: 두 네트워크 잇기

Airflow(docker-compose 네트워크)와 kind(자체 네트워크)는 기본적으로 서로를 모르는 별개의 도커 네트워크다. 잇는 방법은 두 갈래다.

하나는 `host.docker.internal`로, 호스트가 노출한 포트를 컨테이너 안에서 특수 호스트명으로 우회 접근하는 방식이다. 다른 하나는 같은 네트워크에 합류시키는 것인데, 이번엔 이걸 택했다. 컨테이너가 네트워크 여러 개에 동시에 속할 수 있다는 점을 이용해, Airflow 컨테이너를 kind 네트워크에도 연결하면 포트 매핑 없이 컨테이너 이름으로 바로 통신한다.

이걸 쓰려면 compose 입장에서 kind 네트워크는 "내가 만든 게 아니라 이미 있는 것"이므로 `external: true`로 선언한다.

```yaml
services:
  airflow-scheduler:
    networks: [ default, kind ]   # 기존 스택 + kind 컨트롤플레인
networks:
  default: {}
  kind: { external: true }
```

연결되면 컨테이너 안에서 kind 컨트롤플레인 이름으로 K8s API에 직접 도달한다. 호스트가 매핑해준 포트는 호스트 자신을 위한 것이라 다른 컨테이너 안에서는 의미가 없다는 게 이 문제의 핵심이었다.

## KubernetesExecutor를 쓰기 위한 전제조건

1. 패키지 — `apache-airflow-providers-cncf-kubernetes` (DockerOperator용 패키지와는 별개다).
2. 네트워크 연결 — 위 항목.
3. kubeconfig(인증) — 다음 단계.
4. Pod Template — 태스크마다 만들 Pod 스펙 정의.
5. 실행기 전환 — `LocalExecutor` → `KubernetesExecutor`.

다만 다음 장에서 보게 되는데, 목표로 삼은 "태스크마다 격리된 Pod"에는 실행기를 통째로 바꾸는 KubernetesExecutor까지 갈 필요가 없었다.
